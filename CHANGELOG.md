# Changelog

## Unreleased

### Changed

* `rust-public-1` now pins toolchain `1.98.1` (replacing `1.88.0`) with clippy, matching two-bot-next. Its server-owned guest build env (`CARGO_INCREMENTAL=0`, `CARGO_PROFILE_DEV_DEBUG=0`, `CARGO_PROFILE_TEST_DEBUG=0`) gives remote Cargo the same lean settings as `scripts/cargo_cache.py`, and no host env is forwarded. A workspace toolchain file pinning an uninstalled channel stays local; the native backend re-reads it from the host-owned source.

### Fixed

* Offloaded commands now run from the caller's directory. The shim submitted `cwdRelative: "."` regardless of where it was invoked, so `cd crates/foo && cargo test` ran (and reported) the workspace-root command. It now sends the caller's cwd relative to the real `PAPERCLIP_WORKSPACE_CWD` root (both realpath'd); a cwd outside the workspace, or no resolvable root, runs locally (`--dry-run` reports the reason). Cargo honours the toolchain file nearest the run directory, and a Node/Python sub-project with its own lockfile stays local.
* Host-service workloads no longer classify as remote. Any command run with a database/cache env set stays local before any broker call (`*DATABASE_URL`, `*REDIS_URL`, libpq `PG*`, `*TESTDB*`, `*_DB_HOST`; presence only, values never travel). Two-bot-next DB tests skip without that env, so a remote run would have passed with less coverage. Cargo test runs that include ignored tests, use `--all-features` or enable the profile's `db` service feature also stay local: those tests reach `agent-testdb` with no env to detect.
* Path-bearing Cargo options (`--manifest-path`, `--target-dir`, `--out-dir`, `--artifact-dir`, `--lockfile-path`, `-C`) now classify as local, so a dry run agrees with the executor, which already refused them.

## 0.2.3

### Added

* Node and Python heavy-command offload alongside Rust (`node-public-1`, `python-public-1` server profiles; `bin/boat-offload-node`, `bin/boat-offload-python` shims installed as npm/pnpm/yarn/npx and pytest/python/python3, opt-in with `BOAT_OFFLOAD=1`). Narrow classifiers keep watch modes, single-file filters, lint/typecheck/format, install/ci, dev servers, inline `python -c` and unrecognized shapes local. Only long commands go remote: per company/repo/profile/command-signature duration history (last 20, 30-day TTL) gates Node/Python dispatch at `offloadMinExpectedSeconds` (default 120 s); unknown signatures run local first and record via shim reports (`POST /offload/report`) and completed remote runs. Rust behaviour is unchanged. Profiles are opt-in through `offloadProfiles` (default rust only). Frozen sync excludes dependency dirs and build outputs; the guest installs from the lockfile into a per-VM hash-keyed cache (missing/ambiguous lockfile stays local). Repo-root lockfiles are return-eligible. `offloadMonthlyVmHourCap` (default 0) caps tracked monthly VM-hours per company against ledger usage.

* Local-run offload binding (default off, `offloadLocalRunsEnabled`). Runs that stay on the Paperclip host get no `environmentRealizeWorkspace` call, so heavy-command offload had no source authority for them. On `agent.run.started` the plugin now builds the same realization payload from host-owned data only: the event's run and issue, the issue's execution workspace, that workspace's local path, and a scoped key from a Paperclip secret. A whole-run realization is never replaced, and run end drops the executor binding. Adds `events.subscribe`, `execution.workspaces.read` and `secrets.read-ref`; upgrading needs board approval of the capability change.
* Default-OFF stock SSH guest transport with real cgroup-v2 preflight, gated preparation, independently verified guest watchdog, boot/process/cgroup/generation-bound controls and recursive descendant cleanup. Native workspace params supply authorization without new capabilities; an explicit repository allowlist and both company flags are required.
* Frozen source upload through native sync and bounded staged-only return collection, wired to durable pool admission, incremental output, guest interest renewal and the existing native sweep/shutdown lifecycle. Real isolated-sshd acceptance tests cover stock-worker dispatch, watchdogs, cancellation, lost supervisors and no live writeback; a deferred one-VM smoke procedure is capped at 30 VM-minutes.
* Receipt-driven broker/executor adapter with incremental byte-preserving output, scoped client heartbeats and cancellation that waits for guest cleanup and staged return. The company plugin setting `offloadExecutorEnabled` defaults to false; a trusted, lifecycle-enabled executor integration and the separate Cargo shim opt-in are also required. The stock worker requires its separate guest-transport opt-in and native-binding prerequisites; custom lifecycle integrations remain supported.
* Opt-in command offload now keeps a company-scoped workspace and its VM reserved through asynchronous push, execution, collection, staging and durable settlement, including cancellation. Independent workspaces can progress without waiting for an unrelated workspace's reservation.
* Collected adapter data reaches staging intact. Staged/conflict receipts survive durable result reads and replay without applying returned files to the live workspace. Existing void-returning sync adapters remain compatible.

### Fixed

* Local-run offload refuses a run's offload routes to any other agent. On Paperclip 2026.1023.0 an agent API key takes its run id from the unsigned `X-Paperclip-Run-Id` header (only agent JWTs carry a signed `run_id`), so a run id alone did not prove the caller owned the run: another agent in the same company could replay a live local run's id and offload against its workspace. The plugin now records the agent from the host's `agent.run.started` payload and answers 403 `run belongs to another agent` on every `offload_*` route for a different agent. Contract tests (`src/host-contract.test.ts`) drive the real worker over JSON-RPC behind the SDK host capability gate with 2026.1023.0-shaped route input, run events, execution workspaces and secret bindings. The SDK devDependency moves to 2026.1023.0.
* `git push` from a whole-run VM no longer fails with `Paperclip: GitHub capability_missing`. Paperclip's managed `git`/`gh` launchers read the run's GitHub capability from `PAPERCLIP_GITHUB_BROKER_TOKEN`, a run-scoped JWT that the JWT rule dropped. The built-in allowlist now names it, and it is delivered only when the allowlist names it exactly and it has the shape of this run's `github_credentials` capability as `runtime-tools-token.ts` mints it (`scope`, `run_id` equal to `PAPERCLIP_RUN_ID`, unexpired, HS256, one compact token of bounded size, a signature segment of exactly one 32-byte HMAC-SHA256 in 43 base64url characters, and no header or claim key Paperclip does not issue). Any other value under that name, a raw `ghp_`/`github_pat_` token, a forged `<header>.<claims>.ghp_...` value or a malformed value included, is dropped with reason `github_capability_rejected`; no GitHub token is ever sent. `PAPERCLIP_GITHUB_BROKER_URL` stays off the list, so the launcher posts to `PAPERCLIP_API_URL`, the in-VM bridge, which already allows `POST /runtime-tools/github/credentials`. A custom `envAllowlist` must add the exact name `PAPERCLIP_GITHUB_BROKER_TOKEN`.
* `ZDOTDIR` and `BASH_ENV` are on the built-in list, delivered only as this run's managed launcher dir that leads `PATH` (`<workspace>/.paperclip-runtime/paperclip-runner/github/<run id>`, the run id being `PAPERCLIP_RUN_ID` of the same env, or the native runner's `anonymous-<agent id>-<16 hex>` and `native-session-<uuid>` dirs) and its `.bashrc`, so nested and login shells in the VM keep the launcher `git` first on `PATH`. The dir is checked by its shape (absolute, ends with that suffix and holds its parent only once, no `.`, `..` or empty segment, no control character, no `$`, backtick or backslash), so a `remoteWorkspaceDir` with spaces or non-ASCII characters keeps its launcher in login shells, while one that bash would expand in `BASH_ENV` (parameter expansion, command substitution, arithmetic expansion) never runs code in the VM's shells. `remoteWorkspaceDir` itself now rejects `$`, backtick and backslash with a config error. Any other value is dropped with reason `github_launcher_mismatch`. `GIT_*`, `SSH_*`, `GH_CONFIG_DIR` and `PAPERCLIP_GITHUB_BROKER_URL` stay out: the launcher sets them for each operation.
* Python commands from a `uv.lock` plan now run from the checkout `.venv` interpreter (`.venv/bin/<runner>`) with `VIRTUAL_ENV=<checkout>/.venv` and `<checkout>/.venv/bin` prepended to the guest `PATH` for that command only (every other env key stays empty) instead of the system PATH interpreter.
* Registry credential detection now scans at any depth (skipping excluded dirs) and treats `uv.toml` plus `pyproject.toml` uv auth config as stay-local; symlinked `pyproject.toml` stays local without following its target and regular files are read bounded at 256 KiB.
* Node `run` scripts containing deploy, publish, release, push, upload, prod or ship stay local; only exact `build` plus an allowlisted suffix stays remote.
* Pinned `requirements.txt` now requires `name[extras]==version` with `--hash=sha256:` per requirement and rejects pip option lines; malformed, editable or extra-index lines stay local.
* Offload submissions reject NUL and other ASCII control characters in argv with HTTP 400 before workspace lookup, journaling or dispatch; the native SSH executor also refuses them defensively before resolving a pool.
* Successful guest-empty verification releases host shutdown tracking for that command, so long-lived pools do not replay cleanup for every completed command. Failed or uncertain verifications remain tracked and receipts stay readable.
* Guest output polling defers an incomplete JSON-line tail until the next read, avoiding spurious uncertain-execution quarantines when a healthy command's output spans multiple writes. Complete malformed records still fail closed.
* Upgrades retain the installed 0.2.2 capability set instead of requesting `execution.workspaces.read`. Offload workspace authority now uses the host-authored native realization payload, persisted per company/run/workspace. Command dispatch stays default-off, unknown bindings fail closed, and whole-run realization does not depend on optional offload state availability. Otherwise-local executor integrations must register the same native binding before admission.
* Detached command-expiry cancellation uses proactive, explicit-company state access through executor cleanup and the final broker receipt write, so an ended heartbeat invocation cannot let an expired sync-in command start.
* Full offload pools stop and retire idle incompatible VMs before admitting replacements, including stopped or legacy slots. Busy, quarantined and pending-stop ownership stays fenced; regression tests also pin unknown-workspace rejection and immediate quarantine refusal with queueing enabled.
* Warm selection, stopped-VM resume and queued dispatch cannot borrow across company, repository, profile or trust-domain pool boundaries. Persisted bindings preserve isolation after worker restart; uncertain workspace holds remain exclusive even when a spare VM exists.
* Cancellation during collection or staging retains execution evidence, staged changes and an exit-130 cancellation result rather than reporting success or safe local fallback. Post-exit journal transitions share the cancellation fence so a pending state write cannot erase the durable cancellation request.
* Lifecycle recovery keeps distinct unresolved create reservations readable, prevents retired stop retries from losing replacement ownership, retries pending idle/shutdown stops after transient outages, and repairs stop telemetry from the earliest reservation-bound durable observation without attributing it to cancelled tails.
* Long-running commands and native sync publish timestamp-only shared activity heartbeats, so an overlapping manager's idle sweep does not mistake silent work for a stale lease. Single lifecycle-worker topology remains required.
* Monitoring remains on by default, with an explicit `monitoring: false` opt-out for new VMs. An account monitoring refusal has an actionable error and never changes account policy. Snapshot scrub diagnostics no longer echo arbitrary guest output into logs or capture errors; provider-side telemetry retention is documented separately from disk cleanup.
* The size-policy guide now consistently documents the `small` light-work fallback, recommends explicit `default` for heavy builds, and warns on an unmeasured small fallback.

## 0.2.2

### Added

* **Measured VM size policy.** Lease acquisition and reuse pick the cheapest measured size per task class (`sizeCostTable`, refreshed weekly by the offline `recompute-size-cost-table` script), with actual running sizes retained for accounting and budget guards preserved.
* **Heavy-command offload executor.** Shared pool of up to `maxOffloadVms` (default 4) guest VMs: warmest running idle first, then most recently stopped, then create, otherwise a bounded FIFO queue. Idle VMs stop `offloadIdleStopSeconds` (default 15) after the last command, never mid-command. Budget reads `GET /limits` before create/resume and falls back to local execution when starts or compute run low. Per-command usage accounting plus a sanitized expected-cost log line; idempotent by commandId.
* **Durable offload journal and guest receipts.** Command intent is persisted with run-scoped payload identity, bounded retained IDs, restart reconciliation, and guest marker/receipt fences; pre-start cancellation and durable queue refusals are fenced so a stale read can neither clobber a later state nor misreport fallback safety. Live dispatch stays disabled and the existing pool contract is unchanged.

### Fixed

* **Release returns a receipt on stop-accept.** Slow stops keep warm reuse: unknown stop status is retried within the existing bound, stale stopping state resets on reconnect, and confirmation plus usage closure stay under the card lock.
* **Native workspace sync over pinned SSH.** Paired tar-stream sync hooks over the multiplexed SSH session with bounded stream IO, sender-side exclusion matching, ACP refusal before operation payloads, runtime-member omission, VM-owned runtime directory restore after workspace replacement, and interrupted-upload cleanup with remote-job cancel on multiplexed timeout. Live timing has not run.
* Test hygiene: the fake-ssh timeout fixture execs sleep so no grandchild outlives the kill.

### Docs

* Pooled heavy-command offload design proposal and acceptance record (`docs/adr/0001-heavy-command-offload.md`).

## 0.2.1

### Fixed

* **Every run on 0.2.0 failed before it started.** Before each run of an agent with an instructions bundle, Paperclip runs its own `node -e` program through Execute to write `.paperclip-runtime/.gitignore`, and that program refuses a `.paperclip-runtime` that is a symlink ("Unsafe runtime exclusion directory"; tog.22 `agent-instruction-files.ts` `instructionGitExcludeProgram`). Paperclip then fails the run with "Could not exclude agent files from task Git staging". 0.2.0 made the directory a symlink into `/tmp`, so all six full-test runs of 2026-10-23 05:15Z failed there.
* `.paperclip-runtime` is a real 0700 directory again, and the plugin keeps it out of boat's snapshots another way: acquire, a resumed lease, RealizeWorkspace and a resume for a command put the rule `.paperclip-runtime/` into `~/.boatignore` (boat's snapshot ignore file; in the home folder it applies to the whole sandbox, with .gitignore rules) before Paperclip syncs anything. Measured on boat the same day: the per-minute and stop snapshot trees hold each `.paperclip-runtime` as an empty directory, nothing below it, and Paperclip's program passes. A bind mount from `/tmp` was measured too and rejected: boat's snapshot saves what the mount shows under `/home/user`.
* A symlink left by 0.2.0 (or a file) is replaced by a real directory; a real one is kept with its files and made 0700 again (one that Paperclip's `mkdir -p` made is 0755). The workspace root must be a plain path under `$HOME`, where the home `.boatignore` applies; anything else fails the start with `BOAT_RUNTIME_DIR_FAILED`, as does a `~/.boatignore` that cannot take the rule.
* `remoteWorkspaceDir` must be a plain absolute path below `/home/user` (no `.` or `..` segments, no `~` or `$HOME`: it is used as typed). ValidateConfig rejects anything else, and acquire refuses a config saved before this check with `BOAT_CONFIG_INVALID` before it creates or resumes a VM: such a root failed at the runtime directory on every VM, and every attempt spent a start.
* `TAR_OPTIONS="--exclude=.paperclip-runtime"` stays: the host's runtime files are not unpacked on the VM, and a tar an agent packs never holds the run MCP config. The scrub before every stop, delete and capture stays as defense in depth: the agent can edit `~/.boatignore`.
* `stage-package.sh` refuses a dist without the `.boatignore` rule, and a dist that still links the directory into `/tmp`. The tests run Paperclip's program (copied verbatim from tog.22) against the directory, with the 0.2.0 symlink as the failing control.

## 0.2.0

### Security

* **Default-deny run env.** Execute now sends the VM only the env keys that `envAllowlist` names (exact names and `NAME_*` prefixes) and drops the rest, logging each dropped key once per run by name and reason, never by value. Before, every string entry Paperclip passed reached the VM: in the first pilot run (TOG-37420, run eca3f106, 2026-10-22) that was the TWO Bot Next project env with PlanetScale production secrets, and the claude-local adapter also passes the Paperclip server's own process env to its command probe.
* The built-in allowlist covers a Claude Code run through the model-proxy tunnel and Paperclip's sandbox bridge. Names with `TOKEN`, `SECRET`, `PASSWORD` and similar need an exact entry. `PLANETSCALE_`, `CLOUDFLARE_`, `CF_`, `DISCORD_`, `GH_`, `GITHUB_`, `BOAT_` and `ASCII_` names, JWTs (such as Paperclip's run token) and database or credential URLs that leave the VM are never sent.
* Every command script unsets `ASCII_TOKEN` and `BOAT_ID` before the payload starts, and VM setup deletes boat's `export ASCII_TOKEN=` line from `~/.bashrc`, so an agent's shells do not get the token that publishes VM ports on public URLs.
* Every command of Paperclip's ACP process-session launcher is refused (`BOAT_ACP_PROCESS_SESSION_REFUSED`), because it starts the agent from an envelope of the whole launch env that no filter sees. That covers both forms: the inline `PAPERCLIP_PROCESS_SESSION_COMMAND_B64` envelope (up to 64 KiB) and the `process-sessions/<uuid>/command.b64` file that Paperclip uploads in `printf` chunks above 64 KiB, which then launches with only `PAPERCLIP_PROCESS_SESSION_DIR`. A command or argument naming a `/process-sessions` directory or `command.b64`, or an env holding either launcher variable, is refused. The first ACP step (the wrapper-script sync) already fails, so no envelope reaches the VM. `PAPERCLIP_PROCESS_SESSION_DIR` left the built-in allowlist. claude_local defaults to ACP, so agents on boat environments need `engine: cli`.

* **Run JWT on the VM disk.** Paperclip writes the run's MCP config, whose "Paperclip projects" server header carries the run JWT (valid up to 48 h), into the VM as the `mcp-config` runtime asset under `<remoteCwd>/.paperclip-runtime/<adapter>/`, inside `/home/user`, which boat saves in every snapshot. The env allowlist cannot see a file. The plugin now deletes every `.paperclip-runtime/*/mcp-config` and `mcp-config-upload.tar*` under each workspace root it knows of (and under `$HOME`, 6 levels deep) before every stop (release, StopLease, the idle sweep, a failed start), every delete (DestroyLease, per-run release) and every template capture, and checks that none is left. Each match goes to `rm` as one argument (glob loop, `find -exec`), and the counts read NUL-terminated paths, so a file or directory name holding a newline cannot add delete targets. A failed cleanup logs an error and deletes the VM instead of stopping it (below); a template capture is refused (`BOAT_RUNTIME_SCRUB_FAILED`). The README no longer says nothing reaches a VM unless allowlisted. The proper fix, bridge-scoped short-lived MCP tokens, belongs in Paperclip.
* **Runtime directory under /tmp.** Acquire, a resumed lease and RealizeWorkspace make `<root>/.paperclip-runtime` a symlink to a fresh 0700 `/tmp/paperclip-boat-runtime-<32 hex>` directory (one per machine the VM runs on, `runtimeDir` in the lease metadata; a resume within boat's 10-minute machine keep gets the same machine and keeps it) before Paperclip syncs the run's files, and a resume for a command relinks every known root. boat never snapshots `/tmp`, so the run MCP config with the run JWT, and the skills, bridge queue, GitHub launchers and upload tarballs next to it, stay out of the per-minute snapshots (kept up to about a day, downloadable with `boat snapshot pull`) and the stop snapshot. A valid link is kept, so a second run on a running VM keeps the first run's files; anything else is replaced, and a real directory's entries move into `/tmp`. When the link cannot be made, acquire fails with `BOAT_RUNTIME_DIR_FAILED`. The scrub stays as defense in depth.
* **The link survives Paperclip's workspace extract.** Paperclip's inbound workspace tar carries the host workspace's own `.paperclip-runtime/` (tog.22: neither `workspaceArchiveExclude` nor the git overlay copy leaves it out), and for that directory member GNU tar replaced the link with a real directory. If the workspace extract came first, the run MCP config landed on the saved disk. If the asset extract came first, it vanished from the agent's path. Every command script now exports `TAR_OPTIONS="--exclude=.paperclip-runtime ..."` (after the run env, ahead of any `TAR_OPTIONS` already set), so GNU tar skips those members. The link and its `/tmp` files stay, and the host's runtime files are not unpacked on the VM. `--keep-directory-symlink` was rejected: Ubuntu's tar from `1.35+dfsg-3ubuntu0.2` (CVE-2025-45582) refuses to write through a link that leaves the extraction directory. Tests run tog.22's extract commands through Execute's script with a real GNU tar: a plain and a git-overlay workspace, asset extract first and last, plus a control without the script. `stage-package.sh` refuses a build without the exclude.
* **A failed scrub deletes the VM, unless its disk must be kept.** When the scrub before a stop cannot verify that the MCP config is gone (or SSH to the running VM fails), an ordinary release, the sweep and a failed start delete the VM instead of stopping it, and log why: a stop would keep the token in the stop snapshot for 14 days, and a delete also erases the older snapshots. The card's next run starts a fresh VM (from `templateSnapshot` when set). If the delete fails, the VM is stopped after all. A failed start also deletes the VM when the link into `/tmp` failed on the VM itself. One exception: where the disk may hold work that Paperclip still needs, the VM is stopped and its disk kept, with an error log (`stopping the VM and keeping its disk although ...`). That covers StopLease, a release with `resourceDisposition: "stop_and_retain"` (Paperclip sends these to keep a failed run's unexported work, and its export-resume recovery needs the `stopped` receipt; the SDK forbids a delete as their fallback), a forced release of a VM that another run on the card still holds, and a sweep stop of a VM that a run still holds (an active run, or a resumed lease's open run window). The scrub fails most often exactly then (a wedged or out-of-memory VM). With `.paperclip-runtime` in `/tmp` the stop snapshot does not get the MCP config from Paperclip's syncs; a VM set up before the link, or one whose link something else replaced with a real directory, can keep it there (accepted risk).
* A failed start scrubs every workspace root the VM's stored record names, so a new worker reaches roots that only plugin state remembers.
* **Review round 4.** The scrub's walk is checked: `find`'s errors and status are no longer discarded, each runtime and adapter directory must be listable, and a path missing only because a directory above it cannot be searched counts. An unreadable subtree gives `walk=incomplete` (exit 3) instead of a false `found=0 left=0`: a template capture is refused, and release, the sweep and a failed start stop the VM with its disk kept (`keep: incomplete_scan`) instead of deleting it. The scrub matches only `.paperclip-runtime/<one adapter>/mcp-config` and its upload tarballs, so a skill's own `skills/mcp-config/` survives. Env values: a value with anything URL-like in it (also JSON-escaped, percent-encoded, or a bare `user:password@`) is kept only as one whole URL in unambiguous characters, or as JSON whose every URL-like string is one; a parsed prefix is never proof (`https://o/'reilly:pw@github.com/o/r` was kept). JSON values are decoded, so a JWT or `@` behind `\u` escapes is found. A database URL, or a URL with credentials, counts as VM-local only for the literal hosts `localhost`, `127.0.0.1` and `[::1]`, an empty host or a socket path, with no host-override query parameter (`host=`, `hostaddr=`, `service=`, ...; percent-encoded names decoded); hex, octal, decimal and short-dotted IPs and one-label names no longer count. The sweep deletes a stopped VM only under the card lock (an orphan's: a name lock that acquire and ResumeLease also take), after reading boat, plugin state and its own activity again; an orphan's stop re-checks the same way. While a company's state cannot be read, the sweep neither stops nor deletes VMs with no record, which may be that company's. ResumeLease runs under the card lock and, like acquire and a resume for a command, waits for a stop that boat is still saving (`BOAT_STOP_PENDING` when it does not end in time) instead of failing on boat's refusal.
* **A failed start keeps the card's resumed VM** (TOG-37714). When the link or the scrub fails at the start of the card's resumed VM, it is stopped with its disk kept (`keep: resumed_disk`); only a VM that the failed start created is deleted.
* The command now runs as `exec env -u ASCII_TOKEN -u BOAT_ID sh -c <script>`: sshd's login shell becomes a `sh` that never had boat's tokens, so no process between sshd and the command holds them in `/proc/<pid>/environ`. That shell stays the command's parent and exits with its status, so a command killed by signal n reports 128+n; before, the command replaced every shell, sshd reported the signal, and ssh exited 255, which the plugin read as a lost VM (checked against a real OpenSSH 9.6 sshd: SIGTERM gave 255 before, 143 now). The live smoke checks `/proc/$PPID/environ`, every readable ancestor, `/etc/environment` and a SIGTERM exit code.
* The JWT and URL checks on env values run in linear time. A 256 KB `eyJeyJ...` value took 12 s and 256 KB of letters 28 s in the old patterns; any 256 KB value now takes a few milliseconds. JWT matches are unchanged (fuzzed against the old pattern).
* More names count as secrets and need an exact entry: anything ending in `_KEY` (or named `KEY`), `_AUTH` or `_PAT`, and anything with `SIGNING`, `HMAC` or `SALT` in it. `PAPERCLIP_BRIDGE_SIGNING_KEY` and `LC_SESSION_KEY` no longer pass through the built-in `PAPERCLIP_BRIDGE_*` and `LC_*` prefixes.
* The JWT rule matches a JWT anywhere in a value (`Bearer eyJ...`, JSON, headers), not only a whole-value JWT.
* A relative `process-sessions` directory (after a `cd` into the runtime root) is refused like an absolute one.

### Added

* `envAllowlist` driver config, validated: entries must be `NAME` or `NAME_*`; a list that no longer delivers the model-proxy or bridge keys gets a warning. An unset list (or a blank string) stays unset in the normalized config and follows the plugin's built-in list. An empty list (`[]`) sends nothing, and validation warns about it.

* One per-card lock for acquire, release, destroy and the sweep's stop (0fa36d4).
* The idle sweep runs outside host invocations, so the host no longer refuses its state calls (ce7dedd).
* The driver declares `sandboxCapabilities.reusableLeases`, so Paperclip stops a card's VM between runs and resumes it (c674915).
* `reuseLease` survives config normalization (8aa3f71).
